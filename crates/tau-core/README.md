# Tau core

Framework-independent native services used by the GPUI host and the session and observability crates: Pi process ownership and JSONL transport, storage profiles and session discovery, saved transcript projection, settings, file previews, skills and SSH helpers. Pi remains the owner of execution and session files.

Pi transport tests live under `src/pi/tests/`. They cover final-output drain, process cleanup, generation fencing and ownership takeover. The stdio round-trip and transport-fault cases launch `../../scripts/pi-stdio-adapter.ts` through its Bun shebang; keep that script and its test-owned scenario closure under `../../tests/support/pi-scenario/`. They do not require installed Pi, credentials or SSH. Other process tests use local scripted children, including simulated remote cleanup outcomes.

The ignored `saved_transcript::tests::real_pi_saved_projection_parity` check remains an explicit installed-Pi canary, not a default dependency. See `../tau-session/README.md` for the separate session-controller canary.

Remote Pi cleanup uses the existing direct OpenSSH child, not a remote PID or a separate acknowledgement protocol. Closing stdin gives every child a shared one-second grace period within a shared three-second stop deadline. Local cleanup succeeds once the child is reaped; remote cleanup succeeds only for a natural SSH command exit with code `0..254`, assuming OpenSSH's documented remote-command exit-status contract ([ssh(1), EXIT STATUS](https://man.openbsd.org/ssh.1#EXIT_STATUS)). Status `255`, signal/no status, any local kill attempt, or an earlier unconfirmed cleanup leaves a sticky, unusable manager entry: stop/replacement/ownership takeover cannot turn that transport outcome into success. Graceful remote exit `0` remains supported. Only `start_remote` classifies the process as remote; `start_local` and injected `start_command` remain local. This does not verify SSH authentication, executable/configuration/option semantics, remote shell behavior, or descendant lifetime, and does not solve the pre-existing network-partition cleanup limitation. Retrying cannot reconcile sticky uncertainty; no external-cleanup confirmation/reset policy exists yet. Best-effort `shutdown()` retains failed entries while the state lives but returns no acknowledgement and cannot preserve ownership across application termination; callers requiring a release/removal/quit gate must retain failed `stop` receipts rather than infer remote exit from shutdown, transport reaping, or disconnect.
